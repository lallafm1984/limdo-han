# LimDo 루프 엔지니어링 적용 기록

## 목적

외부의 일반적인 자율 개발 루프 사용법에서 LimDo에 도움이 되는 원칙을 선별해 현재 구조에 맞게 적용한다. 이름이나 폴더를 그대로 복제해 상태 원본을 둘로 만들지 않고, 이미 더 강한 LimDo 계약은 유지한다.

## 대응 관계

| 일반 사용법 | LimDo의 단일 진실 | 판정 |
| --- | --- | --- |
| `loop/loop.sh` | `scripts/run-cli-loop.sh` | 기존 사용 |
| `loop/PROMPT.md` | `.loop/cli-worker-prompt.md` | 기존 사용, 6절 구조 강화 |
| `loop/env.sh` | `.loop/env.sh` | 새로 적용 |
| `loop/STOP` | `.loop/STOP`, `.loop/runtime/stop` | 사람이 보기 쉬운 별칭 추가 |
| `docs/DESIGN.md` | `docs/1차-목표-작업-기획서.md`와 디자인 문서 | 기존 문서 유지 |
| `docs/STATUS.md` | `.loop/state.md` | 기존 문서 유지 |
| `docs/feedback/INBOX.md` | `.loop/user-directives.md` | 기존 문서 유지 |
| 날짜별 `logs/` | `logs/YYYY-MM-DD/`와 `.loop/runtime/sessions/` | 날짜별 요약 로그 추가 |
| OS 자동 실행 | `scripts/cli-loop-service.sh`, launchd 템플릿 | 비활성 상태로 준비 |

동일 목적의 문서를 새 이름으로 중복 생성하지 않는 이유는 새 세션이 서로 다른 상태를 읽고 엇갈리는 일을 막기 위해서다.

## 적용한 원칙

### 새 헤드리스 세션

감독자는 매 반복마다 `codex exec --ephemeral --json`을 새로 실행한다. `resume`이나 `fork`를 사용하지 않는다. 대화가 아니라 기획서·상태·이력·피드백 파일이 기억의 원본이다.

### 설정 분리

`.loop/env.sh`에서 모델, 세션 간 대기, 감독자당 최대 세션 수, 연속 프로세스 실패 상한, sandbox 모드를 관리한다. 인증키는 넣지 않는다. 현재 Codex CLI에는 한 실행의 최대 turn 수를 직접 지정하는 옵션이 없으므로 지원하지 않는 옵션을 꾸며 내지 않고, 작업자 지시의 `정확히 한 번 반복`과 감독자 세션 상한으로 범위를 제한한다.

### 날짜별 로그와 기계 판독 출력

각 세션의 전체 JSONL·stderr·최종 응답은 `.loop/runtime/sessions/<run-id>/`에 저장한다. 사람이 빠르게 찾는 날짜별 감독자·세션 요약은 `logs/YYYY-MM-DD/`에 저장한다. JSONL은 thread 시작, 명령, 파일 변경, 완료와 실패를 사후 감사할 수 있게 한다.

### 안전한 중지

`.loop/STOP` 또는 `.loop/runtime/stop`이 있으면 현재 작업자 세션을 강제 종료하지 않고 그 세션이 끝난 다음 감독자가 정상 종료한다. `scripts/stop-cli-loop.sh`가 두 신호를 함께 만든다.

### 같은 고장을 두 번 겪지 않기

같은 사용자 지적이나 같은 근본 원인이 두 번 나타나면 `docs/회귀-규칙.md`에 원인·규칙·근거·기계 검사를 기록한다. 측정 가능한 항목은 같은 루프 또는 바로 다음 결함 루프에서 테스트나 자동화 검사로 고정한다.

### 화면은 직접 판정

화면이 바뀌는 루프는 코드·빌드만으로 완료하지 않는다. 정확한 2340 × 1080에서 실행하고 새 스크린샷 또는 연속 프레임과 hierarchy를 수집해 실제 이미지를 읽은 뒤 디자인·아이 사용성·가림·크기를 판정한다.

### 에뮬레이터는 2시간마다 cold restart

`alarmquest-qa`를 오래 켜 두면 host·guest 메모리 누적과 입력 지연으로 실제 제품 결함이 아닌 버벅임이 섞일 수 있다. 따라서 시각·입력 QA 직전에 Android의 `/proc/uptime` 첫 값을 읽고, 7,200초 이상이면 새 시나리오를 시작하지 않는다.

재시작 순서는 다음으로 고정한다.

1. 현재 serial이 `emulator-5554`, AVD가 `alarmquest-qa`이고 다른 프로젝트가 사용 중이 아닌지 확인한다.
2. `adb -s emulator-5554 emu kill`을 실행한다.
3. `adb devices`에서 `emulator-5554`가 완전히 사라졌는지 확인한다.
4. `/Users/lim/Library/Android/sdk/emulator/emulator -avd alarmquest-qa -no-snapshot-load -no-snapshot-save -no-boot-anim -gpu host`로 새 process를 시작한다.
5. `sys.boot_completed=1`, 물리 1080 × 2340, `user_rotation=1`을 확인한다.
6. 최신 APK를 다시 설치·실행하고 LimDo의 2340 × 1080 화면·focus·시험 상태를 확인한 뒤 검수를 재개한다.

7,200초를 넘긴 뒤 재시작 전에 얻은 새 캡처는 완료 근거로 쓰지 않는다. 재시작 전·후 uptime과 재개 확인은 현재 반복 이력 또는 QA 로그에 남긴다.

## 적용하지 않은 원칙

### 화면 확인 전 커밋

일반 사용법은 자동 검사 뒤 화면을 보기 전에 커밋해 중단 시 작업 유실을 막도록 제안한다. LimDo는 공유 저장소에서 검증되지 않은 UI를 완료 커밋으로 남기지 않고, 자동 검사와 실화면 QA를 모두 통과한 루프만 하나의 체크포인트로 커밋·push하는 더 강한 계약을 사용한다.

세션이 중단돼도 작업 파일은 로컬 작업 트리에 남고 `.loop/state.md`와 `.loop/history.md`가 재개 지점을 기록한다. 따라서 화면 확인 전 커밋 규칙은 적용하지 않는다.

### 자동 실행 즉시 활성화

공용 에뮬레이터를 다른 프로젝트와 함께 사용하므로 launchd 파일을 만들었다는 이유만으로 자동 실행을 켜지 않는다. 사용자가 명시적으로 `켜기`를 요청하고 에뮬레이터 충돌이 없을 때만 활성화한다.

## 로그인 자동 실행 정책

- macOS launchd용 템플릿과 제어 스크립트만 저장소에 둔다.
- PATH와 `CODEX_BIN`, 저장소 경로, 로그 경로를 plist에 절대 경로로 렌더링한다.
- 로그인 시 시작하고 비정상 종료만 재시작한다.
- STOP 또는 작업 없음으로 정상 종료하면 재시작하지 않는다.
- 현재는 설치·활성화하지 않는다.

## 재개 뒤 최초 확인

에뮬레이터 사용이 허용되면 먼저 `./scripts/run-cli-loop.sh --once`를 최대 두 번 실행해 날짜별 로그, 새 thread ID, 한글 지속 기록, STOP 동작을 확인한다. 두 번은 설치 확인 상한이며 통과 뒤 세 번째 확인 루프를 만들지 않는다. 그 후에만 사용자가 원하는 실행 방식으로 감독자를 켠다.
